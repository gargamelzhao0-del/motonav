# MotoNav 0.2.5 驱动检查与性能验证

2026-11-12，COM21，ESP32-S3-Touch-AMOLED-1.75C；ESP-IDF 5.5.4 / Component Manager 2.4.10 / BSP 3.0.0 / LVGL 9.5.0 / adapter 0.6.4。分辨率仍为 466 × 466，CPU 240 MHz、QSPI 40 MHz，没有超频或降低画质。

## 本次实现

- 私有 `qspi_panel.cpp` 使用公开 ESP-IDF LCD IO / SPI 扩展接口，将单线指令和地址与四线像素放入同一片选序列，省去单独的轮询指令事务。厂商 CO5300 复位、初始化参数、列偏移和亮度定义保留。
- 两块 64 行内部 DMA 缓冲各 59,648 字节；根据 S3 单次 32 KiB 的 DMA 上限分段，两个固定描述符循环使用，仅最后一段通知 LVGL。DMA 描述符按硬件分段配置，不再按整幅 434,312 字节画面预留。发送路径不分配内存或复制像素。
- 缓冲必须由真实 DMA 完成回调与 SPI 返回队列共同释放。第二段提交失败时回收已提交的第一段、锁存故障；无法确认回收时终止，避免覆盖 DMA 正在读取的内存。控制命令也先等待像素传输完成。
- SPI 主机发送函数及本地热路径放入 IRAM，减少指令缓存未命中的影响。亮度调用使用 CO5300 正式接口，返回实际错误，不再使用总是返回成功的 BSP 包装。
- 新增默认关闭的驱动计数接口；LVGL 分析器、自动亮度接口检查和测试日志均在可删除的 `tests/device/motonav_bench/` 中。应用只配置 `DisplayConfig` 并调用公开接口。
- 底层 RGB565 填充使用对齐整字写入及有界尾部处理；没有修改道路、路线或显示内容。原有所有 LVGL 预览文件与修改前逐字节一致。
- 触摸已经是 IRQ 触发的 I²C 读取，没有引入空闲轮询。BLE 保持 CPU0 的有界接收与回调，显示及 SPI ISR 保持 CPU1，未修改 NAV3 协议或 Android。

## 对比与淘汰的方案

短对比每项运行 23 秒，去掉 2.5 秒预热后约 20.5 秒、18 个 FPS 采样窗口。它们用于选择方案，最终结果以延长回归为准。

| 实验 | 局部 HUD 最低/平均 | 矩形全屏最低/平均 | 全屏地图最低/平均 | 结论 |
| --- | --- | --- | --- | --- |
| 0.2.4 驱动基线，64 行 | 58 / 59 | 32 / 32 | 36 / 36 | 基线 |
| 32 行 + 通用内存搬移裁剪 | 59 / 59 | 19 / 19 | 26 / 26 | 淘汰；搬移及额外条带绘制开销过大 |
| 64 行 + 整字裁剪 + 新 QSPI | 59 / 59 | 31 / 31 | 36 / 36 | 淘汰通用裁剪；约 2 ms/帧打包开销仍抵消收益 |
| 64 行新 QSPI，不做通用裁剪 | 61 / 61 | 32 / 32 | 36 / 36 | 保留；地图渲染阶段约 25.2 ms |
| 上项 + RGB565 填充优化 | 61 / 61 | 32 / 32 | 36 / 36 | 图像完全一致；整帧 FPS 提升不足 1 FPS |

后两次短测中手机自动加密重连并持续发送等待定位状态，其他基线主要为 BLE 广播空闲，不能把局部 HUD 的差别全归因于单个改动。地图每帧窗口命令耗时由约 517 µs 降到约 340 µs，提交耗时由约 449 µs 降到约 360 µs；这些计时不是互斥阶段，不能简单相加推算 FPS。

实验发现并修复了无参数命令必须关闭 MOSI 数据阶段、32 KiB 单笔 DMA 上限，以及最大事务长度查询必须在 SPI 设备创建之后进行等边界问题。失败实验日志不参与性能结论；相应约束已加入直接编译真实传输实现的主机回归。通用圆角裁剪与打包代码未进入交付源码；地图原有的可见圆形区域刷新继续保留完整物理像素和 3 像素余量。

## 最终回归

每项运行 123 秒、预热后约 120.5 秒，三项连续自动完成：

| 负载 | 最低 / 平均 FPS | 样本数 | 预热后测量 |
| --- | --- | --- | --- |
| 局部 HUD | 61 / 61 | 109 | 120523 ms |
| 矩形全屏重绘 | 33 / 33 | 108 | 120531 ms |
| 466 × 466 全屏模拟地图 | 36 / 37 | 108 | 120525 ms |

390 秒日志无 panic、断言、看门狗、SPI 失败或 DMA 等待超时。三次运行中亮度 70 的实际控制命令成功，越界 101 均被拒绝。手机持续保持认证加密连接，每秒发送等待定位状态；结束时接收计数 373、重复 0、拒绝 0。测试退出后恢复导航页，内部可用 RAM 恢复到 66,771 字节。

用户在本轮全屏地图阶段确认：圆屏边缘、文字、颜色显示正常，无花屏、横向断层或闪烁。自动测试期间没有要求操作触摸；手动长按/短按仍沿用既有实现，未在本轮重新验收。

最终地图命令耗时约 266 µs/帧、提交耗时约 281 µs/帧，渲染阶段约 24.66 ms/帧。与基线的 517 µs、449 µs、25.50 ms 相比，驱动开销确有减少，但整帧改善较小：平均地图 FPS 由约 36 提至 37，最低仍为 36，**全屏至少 40 FPS 未达标**。真实道路导航和更复杂地图负载未验证。

地图阶段内部剩余 RAM 的日志范围：53,707–54,447 字节。


FPS 仍来自最后一块像素 DMA 完成回调，不是 UI 定时器次数。地图负载固定为 7 个路线点、22 条背景道路线段。`driver_profile` 的阶段平均值包含预热，`display_test` 的 FPS 样本排除前 2.5 秒；`transfers` 指逻辑条带，不是拆分后的 DMA 事务数。正常运行不启用这些分析器。

## 性能边界

本次没有证明性能已达到硬件极限，也没有证明任意地图可达 40 FPS。40 MHz 四线总线理论像素带宽为 20 MB/s，完整矩形帧仅像素就需约 21.72 ms，当前地图可见条带约需 19.20 ms；还需要容纳命令、绘制、条带之间的空闲及应用调度。当前主要限制是绘制与传输的流水重叠效率，单纯减小缓冲、裁剪后再搬移并不能解决。

## 交付与证据

6 个主机测试程序与依赖边界检查通过，包括直接编译真实 QSPI 代码的 SDK 替身测试：无参数命令、分段片选、仅末段回调、描述符回收、对齐、过大输入、排队失败和清理。原生 LVGL 6 项测试通过，所有既有 PPM 预览与优化前字节一致。正常生产构建和完全不包含 tests/ 的独立源码构建均成功，通过 verify_production.py。

COM21 已刷回正式版；65 秒日志确认版本 0.2.5、device_tests=0，无测试页面/分析器日志。正式回归时手机未连接，电脑只读 BLE 验证读取版本 0.2.5，确认 RX write、TX notify 后断开，没有请求配对或发送导航报文。手机加密接收计数来自前述长测，不能当作本次正式版道路导航验收。
