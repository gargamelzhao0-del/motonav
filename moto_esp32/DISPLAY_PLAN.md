# 圆屏显示与蓝牙扩展设计草案

2026-11-12，基于已经刷入 COM21 的 0.2.1 固件。本文是下一阶段设计，尚未写入设备，不改变当前 NAV3 协议。App 由另一位开发者维护，固件和显示设计归本目录。

整体架构和实施顺序以 [PROJECT_ARCHITECTURE.md](PROJECT_ARCHITECTURE.md) 为准，主要视觉与交互沿用仓库已有的 [圆屏地图原型](../sim/index.html)。本文作为显示信息清单；前一轮箭头式设计保留为地图未就绪时的降级视图。

## 已具备的基础

- BLE 广播、六位 PIN 配对逻辑、经过身份验证的加密 RX、TX 通知确认、重新握手及断连状态处理已经实现。
- 实机已验证扫描、连接、服务枚举、固件版本读取；用户确认屏幕和长短按正常。手机 PIN 配对、持续导航和道路实测仍需联合验证。
- NAV3 现有字段为导航模式、转向图标、转向距离、剩余里程、剩余时间、车速和来源年龄；暂不传路名、天气、目的地名称、消息、路线几何或电量。
- 当前设备本地局部 HUD 测试最低 59 FPS；强制全屏重绘约 31–32 FPS。采用 ESP32 本地绘制、局部刷新，手机发送语义数据；页面设计仍须在实际导航和 BLE 持续传输时重新测量。

## 显示内容与优先级

| 页面 | 主要内容 | 数据来源和前提 | 实现顺序 |
| --- | --- | --- | --- |
| 导航主屏 | 转向卡、路线小地图、车速、剩余里程/时长和路名；先完成箭头降级视图 | 导航核心字段来自 NAV3；中文路名、真实路线几何需扩展协议及字库 | P0 基础、随后地图 |
| 连接与定位状态 | 待配对、配对码、手机连接、等待导航、数据过期、断连、到达、已结束 | 已有固件状态；具体定位错误原因需 App 显式提供 | P0 |
| 骑行仪表 | 大车速、本次里程、骑行时长、有效航向、当前时间 | 车速来自定位；统计由 App 保存和同步，运动航向须有效 | P1 |
| 天气 | 当前地/目的地天气、温度、降雨概率、更新时间 | App 调用天气服务；必须带地点、来源时间和过期状态 | P1 |
| 行程 | 目的地、剩余里程、预计到达时刻、剩余时长、途经点进度、到达摘要 | 现有剩余量来自 NAV3，其余需扩展消息；到达时刻需可信时钟 | P1 |
| 设备与设置 | 圆屏电量/充电、蓝牙状态、亮度、日夜主题、版本、诊断 | 电量需接入电源管理驱动；手机电量与圆屏电量分别标注 | P0 基础、P1 完善 |
| 可选在线提醒 | 沿途天气、路况、来电提醒 | 仅在数据和权限明确可用时接入；App 配置开关 | P2 |
| 升级界面 | 发现版本、下载、校验、安装、重启、自检成功/失败 | 当前固件无 OTA 分区；需先完成升级分区和恢复方案 | 早期基础阶段 |

不在没有数据的情况下显示油量、转速、胎压等车辆参数。若未来接入车辆或外部传感器，再增加对应卡片；限速也须来自可靠的明确数据，不能按道路外观或等级估算。

## 导航降级视图布局

466 × 466 圆形屏幕，边缘让出圆弧裁切区域。正常主屏采用现有地图原型；地图数据未就绪时，箭头视图保留三个层级：

1. 顶部小状态区：时间、蓝牙连接、圆屏电量或 USB 供电；设备电量未接入时不伪造百分比。
2. 中心主区：大箭头 + 距离，配一行下一道路名称或动作文字；长路名截断，完整名称在停车查看，不使用连续滚动字。
3. 底部辅助区：车速、剩余里程/时长。预计到达时刻只在手机时钟已同步后显示。

临近转向时进一步突出箭头和距离，收起天气和次要行程指标。进入临近状态优先使用 App/导航 SDK 的有效机动状态；若使用距离阈值，作为产品参数另行实测，不在设计中固定为某个通用安全距离。

导航准确性优先于动画。可以让控件颜色、转向图形过渡平滑，不能为获得高帧率而插值出不存在的位置、车速或剩余距离。首期仍约 1 Hz 接收真实导航快照，动画由圆屏本地渲染。

## 异常和提醒行为

- 手机断开或导航过期：隐藏旧箭头和旧转向距离，使用明确状态页；不能让上一条指令继续看起来有效。
- 定位/诱导等待：保留手机上的路线，圆屏显示等待状态。只有 App 明确报告定位原因时，才显示“权限关闭”“定位无效”等具体原因。
- 普通天气、来电等在线提示使用底部短条，不能遮住箭头和转向距离。临近转向时延迟低优先级提示。
- 天气数据展示地点及更新时间。无网络时区分缓存和新数据；缓存过期后不继续标记为实时。屏幕方向和天气风向不混作导航航向。
- 通知默认由 App 选择是否推送；骑行页面不显示长消息正文，详细内容留给停车查看。
- 导航数据优先于天气和通知；断开连接后由 App 作为 BLE central 发起重连，ESP32 恢复广播并等待新的握手。

## 页面与操作

默认显示导航主屏；无导航时显示骑行仪表或连接页。正式交互沿用原型的长按快捷轮盘，首期提供导航、行程、天气和设置四个大入口；短触用于确认/返回或唤醒。重要导航事件返回导航页，不自动轮播天气。当前 0.2.1 的“长按显示测试”在正式交互落地时迁移至停车诊断入口，仍保留 USB 台架测试方式。

首期用大面积触摸区域，不依赖精细拖动、键盘输入或多层菜单。目的地搜索、天气地点选择、消息开关、设备绑定和升级确认放在 App。圆屏亮度先提供手动调整和跟随手机日夜模式；不假定已有环境光传感器。

中文导航需建立字库方案：固定界面词使用子集字库，动态路名使用受控大小的中文字库或字形缓存；未知字有明确替代显示。没有字库支持前，不把浏览器设计预览当作已经完成中文固件。

## App / 固件分工与扩展方式

手机负责定位、算路、导航状态、骑行统计和在线查询；ESP32 负责接收校验、时效判断、页面状态及本地绘制。服务器提供天气或其他在线服务时，第一阶段经 App 获取和转发，不让显示主循环等待网络请求。

保持 NAV3 字节协议不变。新增信息通过带能力协商的独立扩展通道设计，不能向 NAV3 行末直接追加文本。扩展消息的 UUID、消息类型、分片和完整帧格式在实现前形成独立版本化协议文档；下面仅确定数据契约需求，不授权旧版接收器接收这些字段。

| 数据组 | 建议内容 | 更新策略 |
| --- | --- | --- |
| 导航附加信息 | 会话标识、下一路名、目的地、有效状态/原因 | 会话/道路变化时更新，重连后发送完整快照 |
| 骑行统计 | 本次里程、已用时长、有效航向、统计会话 | 约每秒更新；由 App 持久化，圆屏重启后恢复 |
| 设备/手机状态 | 设备电量、充电状态、手机电量、连接状态 | 状态变化或低频刷新，两个电量来源明确区分 |
| 时钟 | 手机时间、时区、同步有效性 | 连接时同步，适当低频校正；不替代单调时钟的导航时效判断 |
| 天气 | 地点、天气类别、温度、降雨概率、来源时间、有效期 | 按服务数据更新频率拉取，内容变化时发送 |
| 提醒 | 类型、优先级、短标题、有效期、去重标识 | 事件触发；排队有界，旧提醒不能挤占导航 |

扩展传输须有明确长度上限、UTF-8 边界、分片重组上限、消息序号和失效规则。导航队列优先；天气和字体等大块资源分批传输，不能阻塞实时导航。设备收到数据后校验范围和来源年龄，不把每次重传当作新数据。

## 下一阶段交付顺序

1. 完成手机 PIN 配对、NAV3 持续传输、断线重连、锁屏运行和定位恢复联调。
2. 中文化主屏与状态页，同时提前验证局部动态地图的渲染预算，冻结扩展协议和共享场景样本。
3. 提前建设固件 OTA：分区迁移、下载校验、安装失败恢复、掉电和重试测试，再交付升级界面。
4. 接入路名、真实路线小地图、轮盘、骑行统计和行程页，验证真实导航负载下至少 40 FPS。
5. 接入设备电量、时钟、天气及低干扰提醒；弱网/缓存/过期状态一起交付。

动态全屏地图作为单独性能项目评估。当前局部 HUD 的 59 FPS 不能用来承诺地图或所有页面均达到 40 FPS；正式验收需同时记录显示帧率、BLE 端到端延迟、断连恢复及数据过期表现。
